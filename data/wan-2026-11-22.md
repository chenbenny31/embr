## What each pass shows

**All four QUIC rows give 1.71 Gbps because the receiver is the limit.** Its process uses
4.82 s of CPU in 5.01 s of wall time, one thread at 96%. What the sender does differently
shows only in the sender's CPU.

**GRO (`gro-off` pass).** With `EMBR_QUIC_GRO=0` the QUIC rows read 1.50 Gbps [1.45, 1.52],
receiver process 5.54–5.58 s, whole host 6.25–6.62 s. GRO on a real NIC is worth 14% of
throughput and 13% of receiver CPU (17% of the whole host's). The veth tests could not show this:
there packets arrived one by one. On ENA a read returns 12.5 datagrams behind a GSO sender and
19–20 behind a sender that sends them singly.

**ACK threshold (`ack10` pass).** Acknowledging every 10 packets changes nothing: 1.71 Gbps,
receiver 4.79–4.83 s, sender 2.25 / 2.33 s. The September finding that the ACK rate matters
belonged to one-datagram reads and sends.

**Slot pool (`slots128` pass).** With 128 slots the `SEND_ZC` + GSO sender never waits (0
against 1,762 waits per transfer) and nothing improves: 1.72 Gbps, sender 2.33 s (2.27 with
8 slots). Waiting for a slot costs no measurable CPU here. The larger pool has a cost, below.

**embr TCP** was in every pass as a drift check: 1.96, 1.94, 1.91, 1.92 Gbps.

## `SEND_ZC` against `sendmsg` on a real NIC

| | `SEND_ZC` | `sendmsg` | difference |
|---|---|---|---|
| One 1345-byte datagram per send: process CPU per GiB | 3.36 s | 3.15 s | `SEND_ZC` +0.21 s |
| same, whole host | 4.06 s | 3.44 s | `SEND_ZC` +0.62 s |
| 15 datagrams (20 kB) per send: process CPU per GiB | 2.27 s | 2.33 s | `SEND_ZC` −0.06 s |
| same, whole host | 2.59 s | 2.58 s | none |
| Datagrams copied by the kernel | 0 | all | |

- The copy is really gone (0 copied in 8.8 million sends, no fallback, no error).
- At one datagram per send, zero-copy costs more than the copy it removes. In the sender's
  profile the extra time is completion handling on the way back to user mode
  (`irqentry_exit_to_user_mode`: 13% of embr's samples with `SEND_ZC`, below the report's
  threshold with `sendmsg`).
- At 20 kB per send the two break even. The 0.06 s process difference repeats in the three
  passes with 8 slots (2.27/2.33, 2.29/2.36, 2.25/2.33) and is gone with 128 slots (2.33/2.33);
  the whole-host numbers do not separate the two (2.59/2.58, 2.70/2.65, 2.45/2.62).
- GSO is what saves sender CPU: −26% for `sendmsg`, −32% for `SEND_ZC`.

### `SEND_ZC` + GSO is the only row that trips AWS's outbound shaper

`bw_out_allowance_exceeded` on the sender's NIC counts packets AWS queued or dropped because
the instance sent faster than its allowance. One row per pass, 1 warmup + 3 timed transfers
(3.3 million packets sent in each):

| row | packets over the allowance |
|---|---|
| `SEND_ZC` + GSO, 8 slots (four passes) | 1,383 / 1,619 / 1,686 / 1,832 |
| `SEND_ZC` + GSO, 128 slots | 13,986 |
| `SEND_ZC` + GSO, 8 slots, receiver GRO off (two passes) | 815 / 1,207 |
| `sendmsg` + GSO (two passes) | 0 / 0 |
| `SEND_ZC`, one datagram per send (two passes) | 0 / 0 |
| `sendmsg`, one datagram per send (two passes) | 0 / 0 |
| embr TCP (two passes) | 197 / 276 |
| nc | 4 |

The same average rate, the same 15-datagram sends, and only the io_uring path is over the
allowance, eight times more with a pool sixteen times larger. The likely reason, not yet
measured directly: queued sends are submitted together, so up to slots × 15 packets reach the
NIC back to back, while `sendmsg` hands over 15 and then encrypts the next 15. Throughput did
not change (the receiver is the limit) and the datagrams sent per transfer rose by 0.06% with
128 slots, so little was dropped. It is an argument for pacing and against a large pool.

Half of the QUIC receiver's CPU is the content hash, at the 437 MB/s this CPU manages without
SHA extensions: 2.46 s of the 4.82 s per GiB. Decryption and the whole of QUIC are 18% together.
The hash is also why embr TCP reads 1.96 against nc's 2.21 Gbps.

## The path and a second connection

| at once | nc | embr TCP | embr QUIC (`sendmsg` + GSO) |
|---|---|---|---|
| 1 transfer | 2.13, 2.16 Gbps | 1.97, 2.05 | 1.71, 1.71 |
| 2 transfers, total | 3.94, 4.29 | 2.69, 2.79, 2.81 | 2.02, 2.02, 2.04 |
| gain | about 2× | +38% | +19% |

The 2.1–2.2 Gbps ceiling is per flow: two plaintext streams carry twice as much. embr gains
much less because each pull's CPU rises when both vCPUs are busy (QUIC user time 3.6 → 6.1 s
per GiB, TCP 2.6 → 4.4 s): the two vCPUs are one core's two threads. On this instance type a
second connection, or a hash thread, can only buy what the second hardware thread is worth.

## What follows from it

1. Default egress: `sendmsg` + GSO does everything `SEND_ZC` + GSO does on this NIC, without
   the slot waits, the locked memory or the shaper hits. `SEND_ZC` saves at most 0.06 s per GiB.
2. The next gain on the receiver is the hash, not the network path: 52% of its CPU. Taking it
   off the connection thread helps in proportion to the spare core, which a c5n.large does not
   have; a CPU with SHA extensions removes most of it with no code change.
3. Pacing is now backed by a measurement (the shaper counter), where before it was a guess.
4. More than one connection is worth about 2× on this path only if the hosts have the cores.

## The run itself

- First smoke test failed at once: the sender printed "serving" when it had started its pushes,
  and the receiver probed TCP 10007 before the push had finished hashing the file and bound the
  port (11 s with five rows hashing at once on this host). `bench/bench.sh` now waits until every
  row's port is bound before it says "serving". The failed attempt is in `smoke-attempt-1/`.
- `ip -s link` printed the network interface's identifier; those lines are removed from the files
  here and `bench/wan.sh` no longer records them.
- `profiles/` were recorded while `single-row/*-profile-*` passes ran, so those passes' timings
  carry the profiler's overhead; use them for the counters, not for throughput claims.
- The first six `single-row/035*`–`0402` passes were recorded for a profile report that was
  replaced; their run files are complete and are kept as extra samples of the shaper counter.
